# 저장 구조 개선

## Issue

인벤토리뿐 아니라 상점, 이벤트, 퀘스트 등 여러 시스템의 상태를 저장해야 했습니다. 기존 JsonUtility 경로는 저장 데이터를 전체 JSON 문자열로 만든 뒤 파일에 기록했습니다. 데이터가 증가하면 문자열 생성과 할당 비용도 함께 증가하므로, 파일 쓰기만 비동기화해도 메인 스레드의 직렬화 비용은 남습니다.

텍스트를 압축하는 방식은 크기를 줄일 수 있지만 압축 연산이 추가됩니다. 따라서 저장 형식을 바이너리로 바꾸고 직렬화 과정에서 재사용할 수 있는 메모리를 분리하는 방향을 선택했습니다.

## Solution

`SaveLoadManager`에서 MemoryPack과 `ArrayBufferWriter<byte>`를 사용하도록 했습니다. 저장마다 버퍼의 사용 영역을 초기화하고 직렬화 결과를 기록하되, 버퍼 자체는 재사용합니다. 저장 요청은 `SemaphoreSlim`으로 직렬 처리하여 이전 파일 쓰기가 사용하는 버퍼를 다음 요청이 덮어쓰지 않도록 했습니다.

파일은 임시 경로에 쓰고, 길이와 역직렬화 가능 여부를 검증한 다음 기존 파일과 교체하도록 했습니다. 불러오기는 파일 스트림에서 역직렬화하여 전체 파일을 별도 바이트 배열로 먼저 읽는 단계를 피했습니다.

```mermaid
flowchart LR
    A[상태 수집] --> B[재사용 버퍼에 직렬화]
    B --> C[임시 파일 기록]
    C --> D[길이와 역직렬화 검증]
    D --> E[기존 파일 교체]
```

## Result

전체 JSON 문자열 생성 경로를 바이너리 직렬화와 버퍼 재사용 경로로 대체했습니다. 저장 요청 사이의 버퍼 소유권을 명확히 하고, 새 파일이 검증되기 전에 기존 파일을 직접 덮어쓰지 않도록 했습니다.

다만 버퍼 확장, 상태 수집, 역직렬화까지 모든 할당이 사라진 것은 아닙니다. 따라서 저장 시스템 전체에 `Zero Allocation`이라는 표현은 사용하지 않습니다. 백업 복구 역시 모든 파일 손상에 대한 자동 복구를 의미하지 않습니다.

## 측정 코드와 해석 범위

- [비교 실행기](../Source/Assets/Editor/SaveLoadBenchmarks/SaveLoadBenchmarkRunner.cs)
- [결과 표시 도구](../Source/Assets/Editor/SaveLoadBenchmarks/SaveLoadBenchmarkResultWindow.cs)

이 코드는 기존 데이터를 복제한 합성 규모에서 JsonUtility와 MemoryPack 경로를 비교한 실험 브랜치의 기록입니다. 원본 게임의 모든 저장 단계나 실제 플레이 프레임 지연을 그대로 측정한 결과는 아닙니다. JSON의 출력 옵션, 데이터 규모와 각 단계의 범위를 맞춰 해석해야 합니다.

기존 GC 이벤트 계측은 Unity `Recorder`의 샘플 수를 사용합니다. 호출 구간의 정확한 할당 바이트를 확정하는 근거로 사용하지 않으며, 이벤트 수가 0이라고 전체 경로가 무할당이라고 결론 내리지 않습니다. 실제 플레이 영향은 Development Build의 CPU Timeline과 GC 할당을 별도로 확인해야 합니다.
